# Tiefenanalyse 2026-10-08 — Stand, Entscheidung, Kandidaten

Fünf Prüfer (Sicherheit, Updates, UI, Funktion, Live-Betrieb) haben Version
0.4.0 gelesen; die Funde stammen größtenteils aus der Code-Lektüre. Dieses
Dokument hält fest, was daraus behoben wurde, was offen ist, und stellt die zwei
Dinge zur Wahl, die eine Entscheidung des Betreibers brauchen. Es ist datiert,
nicht gepflegt.

## Behoben (Commits auf main, jeweils mit Test, der ohne den Fix rot wurde)

| Fund | Fix |
|---|---|
| `Authorization: Bearer x` umging Sudo und CSRF für eine Cookie-Sitzung | Waiver nur für ein aufgelöstes Token (`tokenAuthenticated`) |
| `Host: localhost` von außen umging SSO-only | Loopback-Host von nicht-lokalem Peer gilt als SSO-only |
| kubeconfig/talosconfig/Snapshot/Bundle/Pod-Log ohne Audit | `Route.AuditRead` |
| Argon2 ohne Parallelitätsgrenze; Fehl-Logins nicht im Journal | zwei Slots; WARN mit Peer |
| Audit-Flut durch anonyme POSTs; Sessions nur beim Start gefegt | Token-Bucket je Peer vor dem Audit; Reaper alle 10 min |
| Update-Skript: Downgrade, Prüfsumme optional, Endlosschleife, nicht atomar | siehe `docs/guide.md`, Abschnitt Update-Lauf |
| Job-Abbruch ließ Zombie-Job; SSE-/Supervisor-/Topic-Leaks; `ClearStaged` ohne Aufrufer; Quorum zählte Mitglieder statt Gesunde | `internal/jobs`, `streamhub`, `inventory`, `machineconfig`, `upgrade` |
| UI: Logout bei einem Fehlschlag von `/auth/me`, doppelte Log-Zeilen, stehengebliebener Upgrade-Plan, A11y | `web/src` |

Nicht per Test belegt: die Sperre um `/setup` (Vorsichtsmaßnahme).
Nicht gelaufen: `./bin/task ci`, Browser- und Layout-Tests, `go test -race`.

## Bewusst nicht geändert

- **OIDC-Erstbindung** (erster Anmelder wird gebunden): dokumentiertes Design
  mit Schutz (Konto muss existieren, kein SSO-only-Host, genau ein
  Personenkonto). „Nur aus Admin-Sitzung" wäre ein Umbau des Ablaufs.
- **Sudo für Geheimnis-GETs**: nicht möglich, solange Streaming-Routen nicht
  `Destructive` sein dürfen und die UI die Dateien per Link lädt. Stattdessen Audit.

## Entscheidung: Release-Signatur

Heute: SHA-256 aus demselben Release wie das Archiv. Wer das GitHub-Konto oder
die CI übernimmt, liefert beides konsistent und bekommt root auf dem Pi (das
Update-Skript läuft als root). Eine Signatur hilft nur, wenn der Schlüssel
**nicht** im selben Release liegt und der öffentliche Teil im Skript eingebaut ist.

| | minisign | cosign (keyless, GitHub OIDC) | cosign (eigener Schlüssel) |
|---|---|---|---|
| Vertrauensanker | fester Public Key im Skript | Identität des Workflows (Sigstore, Rekor) | fester Public Key im Skript |
| Schlüsselverwaltung | privater Schlüssel als GitHub-Secret; Verlust = Schlüsselwechsel per Release | keine; Identität = Repo + Workflow-Pfad | wie minisign |
| Gegen kompromittierte CI | nein (CI kennt den Schlüssel) | nein (CI *ist* die Identität) | nein |
| Gegen gestohlenes GitHub-Konto ohne CI | ja, wenn Secret nicht lesbar | teils (Workflow-Pfad wird geprüft) | ja |
| Auf dem Pi nötig | ein kleines Binary (arm64), oder reines Python/openssl-Prüfen | cosign-Binary, Netz zu Sigstore | cosign-Binary |
| Offline prüfbar | ja | nur mit Bundle | ja |
| Aufwand | klein | mittel | mittel |

**Empfehlung: minisign.** Kleinste Angriffsfläche auf dem Pi, offline prüfbar,
kein Sigstore-Netzzugriff in einem Root-Skript. Grenze, die man kennen muss: eine
übernommene CI signiert mit. Dagegen helfen nur ein Umgebungs-Gate mit manueller
Freigabe für den Release-Job und `main`-Beschränkung (siehe unten).

Unabhängig von der Wahl, ohne Schlüssel machbar und sinnvoll:
1. Release-Job nur von `main` (umgesetzt 2026-10-08; die Environment-Freigabe bewusst nicht, der Betreiber will ohne Klick releasen);
2. Actions auf Commit-SHAs gepinnt, Dependabot für `github-actions` (umgesetzt);
3. `govulncheck` in `./bin/task ci` und in der CI (umgesetzt, v1.8.0: keine erreichbare Lücke).

## Kandidaten für fehlende Funktionen (Aufwand grob, ohne Zusage)

| Geplante etcd-Snapshots mit Aufbewahrung und Export | heute nur manuell oder vor Upgrade, lokal, zwei Stück; ohne Off-box-Kopie kein Wiederherstellen bei Verlust des Pi | mittel; Export-Ziel (SFTP/S3) ist eine Entscheidung |

## Offen auf der Betreiberseite

- Ist Port 8443 am Router ins Internet weitergeleitet? Das Journal zeigt etwa 650
  Scanner-Anfragen in acht Tagen. Wenn das nicht gewollt ist: Weiterleitung schließen.
- Ein `next-server` auf Port 3000 ist im LAN erreichbar und gehört nicht zu
  holzkube-manager.
- Die Hardware-Lesewarnungen (rund 400 in acht Tagen, fast nur zwei Knoten)
  koinzidieren mit Last auf dem Pi; Ursache nicht geprüft.
