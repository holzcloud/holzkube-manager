<objective>
An admin action "Unlink single sign-on" for an account (Settings → Accounts). It clears the
account's OIDC binding (model.User Issuer and Subject) so that the next single sign-on from the
LAN address binds the new provider. It exists because the operator moves the production
instance from one OIDC provider to another (new issuer). BindIdentity refuses to move a binding
(ErrAlreadyBound), and the public name is SSO-only. Without an unlink, the operator cannot sign
in there after the switch.

Purpose: the operation BindIdentity's own comment asks for ("unbinding is a deliberate act that
belongs in its own operation"). It is guarded like every other account mutation: admin role,
sudo window, audit record, and refused for service accounts and for accounts with no binding.

Output: auth.Service.UnlinkIdentity, route DELETE /api/v1/users/{id}/identity, the audit
allowlist entry, the problem code conflict.not-linked, linked_provider (issuer host) in the
account view, the page button with its confirm dialog, the provider re-authentication refusal
oidc.not-linked, and the API contract plus guide text (Switching providers).

Two further changes, by operator decision of 2026-10-01 (Task 3):
- first-use linking counts only person accounts, so service accounts no longer block it;
- the SSO-only sign-in pre-check stops answering setup-required merely because several
  accounts exist.

Decisions this plan implements. They are set by the planner; the executor does not revisit them.

- DEC-1 Session: unlinking does NOT end any session, including the session that did it and
  one that signed in through the provider. The reasons:
  (a) A session belongs to the account, and unlinking leaves the account (its ID, role and
  password) unchanged. The binding only decides which account the next provider sign-in
  resolves to. Role changes and admin password resets leave sessions alone for the same reason.
  This server also cannot end another account's sessions selectively: InvalidateAllExcept is
  instance-wide and there is no per-user index. A rule that ended only the clicking session
  would make the result depend on who clicked, not on what was done.
  (b) Ending it gains no security. completeSudo demands a binding that matches the configured
  issuer, so after unlinking, the session can no longer re-authenticate through the provider.
  It can act destructively only until its current sudo window closes. Task 4 gives that
  refusal its own code, oidc.not-linked, so the page explains it.
  (c) Ending it would be actively harmful mid-switch. It would drop the operator on the sign-in
  page while the old provider still holds a live session. On the LAN, with exactly one account,
  one click on single sign-on would silently re-link the identity they just removed
  (first-use binding).
  Consequence for the docs: unlinking stops the next sign-in, not open sessions. Removing an
  account ends its sessions, because CurrentUser re-reads the account on every request.

- DEC-2 More than one account. Operator decision, 2026-10-01: service accounts must not block
  first-use linking. Only person accounts count, meaning accounts that can sign in through the
  provider (Kind person).
  Today bindFirstIdentity uses SingleAccount, which counts EVERY account. Task 3 replaces it
  with SinglePersonAccount, which counts people only.
  After that, first-use linking works with exactly one person account, whatever the number of
  service accounts. With two or more people, no person can be linked or linked again, because
  there is no operation that links a chosen account.
  The unlink action is NOT refused in that case: removing a binding to a dead or compromised
  provider identity is still the right act. Instead, the confirm dialog says so before the
  click (person rows in the list, the same set SinglePersonAccount counts). The guide, the API
  contract and the login page state the person-only rule. The login page's bind-ambiguous text
  currently promises that an admin can link a specific account; that operation does not exist,
  so the text is corrected.
  Production has exactly one account (operator, 2026-10-01), so nothing changes there. The
  more-than-one texts must still be true.

- DEC-7 The pre-check on an SSO-only host (refuseUnlinkedOnSSOOnlyHost). It is a pre-existing
  defect, fixed by operator decision, 2026-10-01. Today it calls SingleAccount, so any instance
  with more than one account answers setup-required, even when an account is linked. The new
  answers, over person accounts only:
  - no person account → setup-required. This includes "no account at all". It also covers the
    edge case of only service accounts, where nothing can be linked either; bindFirstIdentity
    answers setup-required for zero people too.
  - at least one linked person → return false and let the flow proceed. Only the callback can
    tell which subject arrives.
  - people exist but none is linked → bind-host. This is exactly what the callback on this host
    would answer, because bindFirstIdentity refuses an SSO-only host before it counts anything.
    So the pre-check discloses nothing the finished flow would not; that is the argument the
    function's existing doc comment rests on.
  With several people and none linked, the LAN then answers bind-ambiguous. So the bind-host
  login text must not promise that one sign-in on the LAN fixes it; Task 4 softens it.
  Provider sudo (completeSudo) compares only the signed-in account's own binding. No count is
  involved, so it is not affected.

- DEC-3 The route is always registered, in UserRoutes, whether or not a provider is
  configured. A binding left over from a provider that has since been switched off must still
  be removable.

- DEC-4 Response: 200 with the updated account view (the same shape as the role change), so the
  page sees linked_identity false.

- DEC-5 The service-account refusal reuses conflict.not-a-person (the mirror of
  conflict.not-a-service-account, already in the contract), with its doc comment and contract
  row widened. The unbound refusal mints conflict.not-linked.

- DEC-6 README unchanged. Its "Safe by default" bullet already names single sign-on, and
  unlinking is an admin detail whose depth belongs in docs/guide.md. No changelog entry here:
  the release step writes it. The SUMMARY carries operator-facing release-note sentences for
  it, one per change (see output).
