<objective>
The operator decided on 2026-09-30 that HACT-04 ("Der Betreiber kann ‚jetzt nach Updates suchen' auslösen") is not met by "Check for updates and install" alone. This plan adds a fifth host action, **Check for updates**, that only looks and installs nothing, and makes its answer visible on /host -- whether a newer release exists and which one. "Check for updates and install" stays exactly as it is. This is the deferred idea of 13-CONTEXT ("Eine reine ‚nur nachsehen'-Aktion neben ‚suchen und installieren', falls der Betreiber D-06 umwirft"), promoted by that decision; D-01, D-06, D-07 and D-08 gain a fifth entry, and everything else they fix (one line, one slot, consume first, the fixed argv, the four locks, typing for every host action) holds for it unchanged.

Purpose: the operator can ask "is there a newer release?" from /host and get the answer without anything being installed, through the same root helper and the same update script the hourly timer runs.
Output: the fifth order end to end (button, locks, order, helper, a new shipped check unit, the answer back on the page), the helper's order list held as a contract (an older helper refuses the new word; a marker line names the words), the check unit verified and proven to install nothing, and the install commands, guide block, fixture and release archive carrying the new unit. Plan 13-13 then makes the page say when an installed helper is too old for the check, and brings README, guide, picture and the full gate.

This plan does not mark HACT-04 complete: the feature is not done until README says so (CLAUDE.md), which is 13-13's last task, as 13-09 did for the phase.
</objective>

## Decisions this plan takes, with the evidence

**1. The check goes through the helper as a fifth order, `check-update`; the helper starts a new shipped oneshot unit, `holzkube-manager-update-check.service`, that runs the update script's own `--check`.**

Evidence, read at planning:
- `deploy/holzkube-manager-update.sh` already has the check. Its usage says `sudo holzkube-manager-update --check   # nur nachsehen, nichts anfassen`; the `CHECK_ONLY` branch (lines 346-355) compares the installed version with the newest release and exits before anything is downloaded, setting `OUTCOME=current` or `available`, which the one EXIT trap records in `/var/lib/holzkube-manager-update/status.json`.
- The daemon already reads that file. `internal/host/updatestatus` knows `OutcomeAvailable` ("--check found a newer release and changed nothing"), `GET /api/v1/host` carries it as `service.update`, /host shows it under Update check, and the status box's "update finished" phase reads its `checked_at`. The answer reaches the page with no new reader.
- The check path is tested (`TestUpdateScript`: "check current", "check available", "check with the release list unreadable"). What no test says yet is that it installs nothing; Task 2 adds that.
- The record is written only by root: as root, `record_status` wants the directory root-owned and not group- or other-writable; otherwise it must be writable, which the daemon's user is not. So root has to run the check.

Alternatives, rejected with their reasons:
- **A. The daemon asks GitHub itself** (it has AF_INET and already reaches factory.talos.dev). It would be a second implementation of the release selection (the first non-draft of `/releases?per_page=20`, exactly one `holzkube-manager_*linux_<arch>.tar.gz`) in another language. It cannot read `/etc/holzkube-manager/github-token` (root, 0600) or the `REPO` override in `/etc/holzkube-manager/update.conf` (a shell file root sources), so it could report a release the updater would not install. It would put a second "latest" beside status.json on the same page. And the phase goal has every host action go through an order to the root helper "nach dem Muster von holzkube-manager-update", with D-06's "genau einen Update-Weg".
- **B. The helper runs the update script itself.** Impossible in its sandbox: `RestrictAddressFamilies=AF_UNIX` (no curl to GitHub) and `ProtectSystem=strict` with only its state directory and the order directory writable (no status.json). Loosening the sandbox of the service that reboots the host, for all five orders, is the wrong trade.
- **C. The helper starts a transient unit with `systemd-run`.** No new file to install, but the sandbox would live in the script's argv, where the systemd-analyze gate (R7) cannot see it, and a second binary joins root's path.

**2. The check arm blocks; the update arm keeps `--no-block`.** A oneshot's start job ends when its ExecStart ends, so a check that fails (GitHub unreachable: the script records `failed` and exits 1; an ExecStart that does not exist) makes `systemctl` fail, and the helper records `failed` for that id at once. With `--no-block` a unit that never ran would leave the page waiting until "no answer". The check unit's `TimeoutStartSec=2min` stays below the helper service's `3min`; curl in the script is bounded by `--max-time 30`. While a check runs the helper service is busy; the page keeps the buttons off during a started check (reason "An update check is running").

**3. All four locks, as for the other four.** HACT-05: "Jede Host-Aktion verlangt Sudo-Fenster und getippten Hostnamen, läuft durch den Audit-Pfad und ist nur ab Rolle Operator erlaubt"; ROADMAP criterion 1 names "jetzt nach Updates suchen" among the actions that need all four; 13-CONTEXT rejected "Tipp-Pflicht nur für Herunterfahren" because HACT-05 wants typing for every host action. The check changes nothing, but it is root acting on the host on the page's behalf, with network and the release token. So: `Destructive`, `MinRole: RoleOperator`, `hostTypedPhrase` true, audit `host.check-update`. D-09's reason (the machine goes away) does not carry over, and the code comment says the reason that does.

**4. Harmless first.** Order in the group: Check for updates · Check for updates and install · Restart service · (16 px) · Restart host · Shut down host. Below md the check spans the grid's first row; under it the service pair and the machine pair keep 13-UI-SPEC's two rows of two. Decided without asking, as 13-UI-SPEC's layout decisions were; the 14 layout audit measures the whole group, so it needs no change.

**5. Reversibility: costly, not one-way, so no checkpoint.** The order word and the new unit join the contract with root code the operator installs by hand. But no release carries the helper yet (the last tag, v0.1.0, is from 2026-09-26; the helper arrived on 2026-09-29), and the operator's Pi has none installed (13-09 to 13-11 checked both files absent). Retiring the word later is a daemon-only change; the helper's refusal of every unknown word covers the other direction, which Task 2 proves on the frozen older helper; 13-13 detects older helpers from the marker line, which is additive by design (no line means the four orders of 13-01).

**6. A defect in the branch this plan edits.** `orderPhase` calls an update finished when the status file's `checked_at` is later than `placed_at`. `checked_at` has whole seconds and `placed_at` sub-second precision, so a run that finishes within the same second as the placement never finishes on the page (it waits 15 min for "no answer"). An update run that finds nothing new can do that; a check will do it often. Task 1 compares against the placement truncated to the second, for both, red first.
