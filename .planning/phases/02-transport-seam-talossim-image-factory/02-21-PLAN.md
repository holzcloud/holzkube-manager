<task type="checkpoint:decision" gate="blocking">
  <decision>Whether a schematic record's identity carries the architecture, or one record carries per-architecture verdicts, or neither</decision>
  <context>
The record's id is the Factory's schematic id, which is the SHA-256 of the canonical document. The
canonical document has no architecture in it — by upstream's design, because a schematic describes
what goes into an image and not what the image is built for. So two records that differ only in
architecture collide: POSTing the same customisation at a second architecture returns
`409 store.conflict`, verified live.

Plan 02-13 added `model.Schematic.Arch` so a verdict names the architecture it is about. What this
gap observes is the consequence nobody wrote down: that field's value is fixed by the identity that
cannot vary with it. One customisation holds exactly one architecture's verdict, and getting the
other one means deleting the first.

The constraint that shapes every option: the record id being the Factory's id is what makes a
schematic findable at all. The Factory offers no way to enumerate schematics, so the stored record is
the only place that id can be read back from. Any option that changes the record's identity has to
keep the Factory's id retrievable, or it trades one unrecoverable thing for another.

This is deliberately a decision and not an implementation. A store schema change in a records-
correction plan would be the wrong place for it; whichever option is chosen, the code lands in a
scoped item elsewhere.
  </context>
  <options>
    <option id="option-a">
      <name>The store key becomes (schematic id, architecture); the Factory id stays a field</name>
      <pros>Two architectures of one customisation coexist, each with its own probe verdict, which is what an operator running mixed hardware actually has. The Factory id remains readable from every record.</pros>
      <cons>The store key stops being the schematic id, so every existing route, link and stored reference that treats them as the same thing has to be revisited, and a migration has to rewrite existing keys. The largest change of the three.</cons>
    </option>
    <option id="option-b">
      <name>One record, per-architecture verdicts</name>
      <pros>Identity is untouched — the record id stays the Factory id. It also models the truth more closely than the current shape does: `usable`, `probed_at` and `probe_reason` were always per-architecture facts stored as if they were properties of the schematic. `409` on a second architecture stops being a wrong answer, because there is nothing to create.</pros>
      <cons>A schema change to three fields that are read in the API, the store and the UI, plus a migration that has to place an existing record's verdict under the architecture plan 02-13 stamped — and under no architecture at all for records written before that.</cons>
    </option>
    <option id="option-c">
      <name>Leave the shape; state the constraint</name>
      <pros>No schema change, no migration. The constraint is written into `model.go`, into the contract and into the ledger, so an operator who meets the `409` finds an explanation rather than a bug, and a later phase can pick it up with the decision already reasoned through.</pros>
      <cons>Probing the other architecture still means destroying a record, and the `409` still reads as "this schematic exists" when the honest answer is "this schematic exists, probed for something else".</cons>
    </option>
  </options>
  <recommendation>Option B as the target, Option C as this round's action. B is the model that matches the facts and leaves identity alone, which is the property worth protecting; but it is a schema and migration change and this is a records plan. So: record B as the decided direction with its reasoning, do C's writing now — the constraint stated in the model, the contract and the ledger — and scope B's implementation as an item for the phase that next touches the schematic store. Option A is not recommended: it pays with the record id, which is the one identifier nothing else in the system can reproduce.</recommendation>
  <resume-signal>Reply with the option id, and say whether the implementation is scoped now or left to the phase that next opens the store.</resume-signal>
</task>
