<objective>
Close G-02-19 and G-02-14: two small, independent corrections in the images route, both of which
make a later plan's work measurable.

Purpose: G-02-19 first, because it blocks G-02-10. `DialogContent` carries `sm:max-w-sm` and the
caller adds `max-w-3xl`; tailwind-merge treats them as different groups because of the variant
prefix, so both survive and the `sm:` rule wins. The measured dialog width is 384px at a 1200px
viewport — the asset panel is permanently cramped at every viewport and `max-w-3xl` is dead code.
Any width-based mitigation for the hyphen-break defect tuned against that is tuned against a bug
rather than against the intended layout, which is why this lands before plan 02-17 measures
anything.

G-02-14 second, and it is one line. `UsabilityVerdict` tests `if (usable)` and returns
"Usable — the build probe confirmed it" before it ever reaches `if (!isProbed(probedAt))`, so a
record with `usable: true` and a zero `probed_at` renders the affirmative verdict. It was reproduced
live from a planted fixture in both the list and the dialog. It is not reachable through today's
POST path, but any migration, import, re-probe or hand-edited record produces it — and T-02-62 says
no state may make a stronger claim than the record supports. The fix is the reordering; the point of
the plan is the test that would have caught it.

Output: a dialog that can use the screen, a verdict that asks whether there is one before asserting
what it is, and a regression test for each.
</objective>

Give the caller a width class in the same merge group *and the same variant* as the default it needs
to beat. `sm:max-w-sm` and an unprefixed `max-w-3xl` are different keys to tailwind-merge, so the
caller's class is kept and then loses in the cascade; a prefixed class at the same breakpoint
replaces it outright. Keep the small-screen behaviour the component defines — below the breakpoint
the dialog should still be the viewport minus its margin, which is what the base class already says
and what the caller must not override.

Write a comment at the call site naming the trap, in one or two lines: the reason the obvious
unprefixed class does nothing is that the variant prefix puts it in a different merge group, and the
next person to widen a dialog here will otherwise repeat it exactly.

Then the test. jsdom lays nothing out, so this test asserts the mechanism rather than the pixels: it
renders the detail dialog, reads the dialog element's `class` attribute, and asserts that the
component's narrow default is no longer present on the element and that the wide rule at the same
breakpoint is. That is not a proxy for a layout property — it *is* the defect, which was a merge
outcome and not a rendering one. Name the test for the merge, not for the width, so it does not
promise something jsdom cannot check.

Say in the test's comment where the pixel measurement lives: plan 02-17 adds the browser runner, and
its first assertion is that this dialog is wider than the old 384px at a wide viewport. This test
and that one are halves of one claim and each should name the other.
