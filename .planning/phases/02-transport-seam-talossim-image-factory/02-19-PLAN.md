Close G-02-15: the assets route answers with no references at all when the installer cannot be
resolved, and the contract describes something milder than what the code does.

Purpose: this is the half of T-02-53 the user explicitly did **not** ratify. The ratified half —
never substitute an ordinary installer for a SecureBoot request — stands unchanged and is not in
scope. What was refused is the coupling of that rule with answering with nothing at all. ISO, PXE,
disk-image and cmdline are built at `schematics.go:400-420` by pure string assembly that never
touches the registry, and `if err != nil { return }` at `:432-436` throws all four away because a
fifth value could not be resolved. Both adversarial reviewers converged on this independently and it
is confirmed in source.

The description makes it worse rather than better. `docs/api-contract.md:655` says the route answers
with "no installer reference" while the code returns no references at all, so the description shown
to the human ratifying the new 502 path was materially milder than the behaviour. The UAT lists
writing the real atomicity into the contract as required before ship, one way or the other.

The branch is reachable today without any SecureBoot name failing: a cold `?secureboot=true` request
was measured at 49.8s of a 60s write timeout, and at v1.13.8 at 60.002s returning HTTP 000 with the
connection dropped. So the common way an operator meets this is a timeout, not a verdict — and the
client's one hardcoded sentence tells them neither. It never reads `assets.error`, never names
SecureBoot, never suggests unticking the box, and no test covers the branch at all.

Output: a response that returns what was computed, a message that says which of the two things
happened, and a contract that matches.

  <context>
The behaviour is decided: the four registry-free references are returned and the installer alone is
marked unresolved. What is not decided is the shape, and the shape is a contract change that clients
match on, so it is worth one deliberate choice rather than a shape that emerges from an edit.

The constraint that rules out the easy answer: `docs/api-contract.md` currently defines
`warnings: []` on this route as meaning the installer repository name was **proven**. A `200` whose
`installer` is an empty string and whose `warnings` is empty would therefore carry an affirmative
claim of proof about a reference that does not exist. Whatever shape is chosen has to make the
unresolved case unmistakable to a client that was written before it existed.

There is a fourth outcome now, where the contract describes three: proven, provisional, refused —
and now "the installer could not be resolved, and here is everything else".
  </context>
