<task type="checkpoint:decision" gate="blocking">
  <decision>The audit actor vocabulary for mutations that no HTTP request initiated (D-10)</decision>
  <context>
Today `internal/httpapi/router.go`'s `auditAdapter` is the only place `Actor` is set in
production code, and it fills it from the request context: the signed-in username, or
`anonymous`. Phase 6's jobs engine becomes the second writer, and a job's mutation has no
request and no signed-in user behind it.

`Record.Actor` is part of the hash chain — it is in `canonicalFields`, so its value is hashed
into every subsequent record. That makes the **format** a one-way decision: changing it later
forces either a chain break at the seam or a rewrite migration across the whole archive, and
D-16 gives the archive unlimited retention and no deletion path. Deciding the vocabulary while
there is exactly one writer is far cheaper than reconciling two conventions later.

D-10 proposes: `system` for a process-initiated mutation, and `job:<id>` reserved now for
Phase 6's jobs engine. The adapter itself stays in the HTTP layer for now; promoting it to a
shared exported type is Phase 6's work and is already recorded as deferred.

This plan writes the decision into `docs/api-contract.md` alongside the existing actor
semantics. No code in Phase 2 writes either value — there is no non-HTTP mutation writer yet —
so what is being fixed here is the vocabulary, not an implementation.
  </context>
  <options>
    <option id="option-a">
      <name>`system` and `job:&lt;id&gt;`, documented now, unused until Phase 6 (D-10 as proposed)</name>
      <pros>Two values, both self-describing, both distinguishable from any username by their shape; `job:&lt;id&gt;` carries the identifier that makes a post-mortem possible ("which job did this"); decided while one writer exists, so no reconciliation is ever needed.</pros>

`dryrun.go`. `var ErrDryRun` as a package-level sentinel with the rationale comment saying it
is a refusal and never a retryable condition. `func dryRunInterceptor(enabled bool) (grpc.UnaryClientInterceptor, grpc.StreamClientInterceptor)`
— a pair of gRPC client interceptors that consult the `ClassMutation` membership of the
invoked full method name and return `ErrDryRun` before the invoker is called. The gate reads
the deadline class table from `deadline.go` rather than keeping a second list of mutating
methods, because two lists is how the next mutating RPC gets missed.

Install the interceptors in the **single shared connect helper** plan 02-05 factored out, so
both `ClusterClient` and `MaintenanceClient` get them and no constructor can forget. That is
the structural half of D-03: the refusal lives at the last layer before the wire, which is the
only layer where "no mutation reached a node" is a statement about the node.

The refusal message follows `tlsx.LoopbackGuard`'s shape: what was refused (the RPC by name),
why (the process was started with `--dry-run`), and what would have to change (restart without
the flag). It is a structural refusal, not an advisory log line, and the doc comment says so
along with the counterfactual: an HTTP middleware check would only see HTTP requests and would
miss anything Phase 6's jobs engine drives, and the `Destructive` route flag is a different
property — destructive and mutating are not the same set.

`dryrun_test.go`. The proof, in three parts.

First, the enumeration: iterate every method the class table marks `ClassMutation`, call each
through both client types against a live `talossim`, assert `errors.Is(err, ErrDryRun)`, and
assert the sim's counter for that method is zero. Iterating the table rather than hand-listing
methods is what makes a mutating RPC added in Phase 8 automatically covered.

Second, the negative control: run the same enumeration with dry-run off and assert the
counters advance. Without this, a gate that refused everything — or a sim that recorded
nothing — would pass part one.

Third, the bypass proof: extend the AST guard so that, in addition to the existing
"no address above the seam" assertion, no production package outside `internal/talos`
constructs a machinery client, and every construction path inside `internal/talos` routes
through the shared connect helper. Report the number of files and construction sites
inspected, and fail on an implausibly low count, so a broken walk cannot pass as a clean one.
