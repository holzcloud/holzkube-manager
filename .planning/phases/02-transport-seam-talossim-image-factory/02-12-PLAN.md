<objective>
Close G-02-3: an installer repository name reached past a candidate that never answered must say so,
must not be frozen for the life of the process, and must be visible to the operator on the panel
that shows the reference.

Purpose: `resolveInstallerRepo` treats a transport failure on the platform-prefixed candidate
exactly as it treats a 404 — it records "unanswered", continues, and on a 2xx from the legacy
candidate returns that name and discards the fully formed error. `installerRepo` then caches it with
no TTL and no provenance. Directly observed across two processes against one schematic at one
version: process 1 served the legacy `installer` name from cache for its whole lifetime; process 2,
started minutes later with a cold cache, served `metal-installer` from then on. Same question, two
answers, split exactly at the restart, with nothing on screen saying the preferred name had never
actually been ruled out.

The fallback stays. 02-04-PLAN.md specifies it deliberately for a connection failure, and
02-04-SUMMARY.md records that factory.talos.dev throttles without an HTTP response at all — a hard
error here would leave an operator unable to read their own asset URLs because a third party was
busy. What changes is that the answer is labelled and no longer frozen.

**Labelled and no longer frozen, not "never remembered".** The UAT's remedy reads "do not cache a
name reached past an unanswered earlier candidate, or re-probe on the next request", and both of
those variants cost the same thing: the silent candidate's full 30s client timeout on *every*
subsequent request, for as long as the candidate stays silent. The route this lands on is the one
whose worst case already equals the response budget. Get the two measured numbers the right way
round, because an earlier revision of this plan did not and built its argument on the wrong one:

- **60.002s is the worst case.** Both candidates silent is 2 x `DefaultTimeout` = 60.000s against
  `writeTimeout = 60s` (`cmd/holzkubed/main.go:44`) — equal, not inside. G-02-2 recorded it:
  `GET .../assets status=502 duration=1m0.002907792s`.
- **43.42s was a success, not the ceiling.** One candidate silent (30s) and the other answering
  (13.4s). It is the *observed* cost of the exact case this plan is about, and it is what the
  operator waited through before seeing a reference at all.
- **218µs is the cached answer.** That is what the second request cost.

Refusing to remember would make one of the first two numbers the cost of *every* subsequent
request, on a route whose ceiling has already been hit, and the operator would then see neither the
reference nor the warning this plan exists to show them — in exactly the throttled-registry case
that motivates the gap.

So the answer is remembered *provisionally*: cached with its warning, served with that warning on
every answer, and re-questioned once the entry is older than a short interval. **And the
re-question asks only the candidate that was never ruled out.** That second half is what makes the
first half safe. The candidate that answered 2xx is already in hand — re-asking it learns nothing
this plan needs — while the candidate that stayed silent is the entire open question. Asking one
candidate makes the re-question at most 1 x 30s rather than 2 x 30s, which is 30s under a 60s
`writeTimeout` instead of exactly at it. Without that narrowing, the one request per interval that
re-questions would itself be the 60.002s shape, and this plan's own must_have — that a registry
which goes silent after answering once never turns a working assets route into a 502 — would be
unachievable as written.

The process-lifetime freeze that produced two processes disagreeing about one schematic is
therefore gone, and nothing this plan adds can reach the response budget. What it does *not* fix is
the cold path: a first resolution with an empty cache is still the 2 x 30s = 60.000s walk, and
`POST /api/v1/schematics` is still three serial calls at 90s. Those are G-02-2's and cluster A's.
Task 1 records the residue in `.planning/WINDOWS.md` and lands the composition guard test the
decision document asks for, so the arithmetic that let `2 x 30 == 60` ship is asserted rather than
re-derived by the next reader.

Output: a warning code and its emission, an assets response that carries warnings, a panel that
renders them, a reference that cannot wrap mid-token, a badge that stops overstating what was
proven, and a route-by-route budget composition table.
</objective>

## Interaction with the open probe-budget decision

This plan touches the surface `02-DECISION-probe-budget.md` argues over, so the boundaries are
explicit:

1. **Option 2's concurrent-candidate variant would move where this warning is emitted, not whether
   it exists.** The decision document notes that probing the installer candidates concurrently under
   one shared deadline "would also close G-02-3's silent-fallback window for free". It would not
   close it: a candidate that is still silent when the shared deadline expires is the same
   unanswered candidate, and the answer taken from the other one is still provisional. What changes
   is that `resolveInstallerRepo` walks the list differently. The warning code, the `warnings` field
   on the assets response, the client schema and the panel rendering all survive that change
   untouched, and task 1's retained-error mechanism is the same either way. Nothing here should be
   deferred in anticipation of it.
2. **No budget and no deadline is introduced; one cache-freshness bound is, and only for provisional
   entries.** Task 1 adds a re-question interval that governs *unproven* installer-repo entries.
   A proven entry still never expires, so WINDOWS entry 15 ("the installer repository cache never
   expires") stays open and is not this plan's to close. Nothing here bounds how long a request may
   take: `DefaultTimeout`, `writeTimeout` and the absent per-route deadline are untouched and remain
   cluster A's. The interval exists because the alternative — the UAT's literal "do not cache" —
   converts a one-time cold resolution into a per-request cost on the route the UAT measured a 502
   at, which would defeat this plan's own must_have.
3. **The re-question is narrowed to one candidate, and that is a correctness constraint rather than
   an optimisation.** Asking the full candidate list on a re-question would put the 2 x
   `DefaultTimeout` = 60.000s composition — the one that equals `writeTimeout` and that G-02-2
   recorded a 502 at — onto the *warm* path, once per interval, on a route that was answering from
   cache in 218µs. Asking only the never-ruled-out candidate makes it 1 x 30s, which is 30s of
   headroom. This is why must_haves truth 5 is achievable at all. The residue this plan does not
   remove is the **cold** path, unchanged: 2 x 30s for assets and 3 x 30s for create. Task 1 records
   it in `.planning/WINDOWS.md` and declares it in the composition guard, and hands it to whoever
   picks up G-02-2 rather than absorbing it here.
4. **The composition guard asserts the existing budgets; it does not set any.** It reads
   `writeTimeout` and `imagefactory.DefaultTimeout` and declares the two routes that do not fit as
   known-over-budget against G-02-2. Whichever option the decision lands, that table is where the
   fix gets proven: Option 1 removes `ProbeBuildable` from the create route's sequential count, and
   Option 2 changes the client timeout the table multiplies by. Either way the row has to be flipped
   deliberately, which is the point.
5. **The badge copy is a copy change only.** It is on the decision document's unconditional list and
   is included here for exactly that reason. If closing it appears to require a third probe state,
   stop — that means the boundary has been crossed and the decision has to land first.
