places the badge appears — plus a ledger entry for the records that can never be qualified.

`model.go`: add `Arch string` with the JSON tag `arch`, placed beside `TalosVersion` because it is
the same kind of fact and reads as a pair with it. Its doc comment states three things, in the
register the surrounding fields use.

First, what it is: the architecture the schematic was authored and probed against. The probe verdict
is scoped to it — `ProbeReason` already carries the architecture inside its sentence, which is the
evidence that the verdict was never architecture-neutral — so `Usable` without it is a claim whose
subject is missing.

Second, why it is on the record rather than a query parameter, which is the same argument
`TalosVersion` makes: the answer differs per architecture, so a stored verdict that does not name one
cannot be read back.

Third, why the field is additive and unversioned, citing `ProbeReason`'s own paragraph rather than
restating it at length: a record written before this field existed decodes with an empty
architecture, and an empty architecture is a true statement about such a record — nothing is
recoverable for a migration to write, because the architecture a past probe used is not derivable
from anything the record holds. Say that last clause explicitly; it is the reason there is no
backfill and the reason task 2 files a window.

`schematics.go`: stamp it in the `rec` literal, `Arch: in.Arch`, beside `TalosVersion`. It is
`in.Arch` and not a value read back from `authored`, because `in.Arch` is exactly what was handed to
`Author` and therefore exactly what the probe used.

Stamp it unconditionally, unlike `probedAt`. The two are different statements and the difference
matters: `ProbedAt` records whether an answer arrived, while `Arch` records what the question was
about. A record whose probe never answered still has an architecture it *was* asked about, and
withholding it would recreate in miniature the ambiguity this gap is about. Write that distinction
into a comment beside the stamp, because the `ProbedAt` conditional is three lines above and invites
the symmetry.

Do not touch `assetRequest`. Reading `rec.Arch` as a default for `?arch=` is the obvious next
thought and it is wrong: the comment at 512-518 argues FACT-03 — holzkube is developed on arm64 and
targets amd64, so a defaulted architecture is a bug that only ever appears on someone else's
machine. The record's architecture is a description of what was probed, not a preference for what to
ask about next. Add one sentence to that comment saying the record now carries an architecture and
that it is deliberately not used here, so the next reader finds the decision rather than the
omission.

Do not touch the 409 path. It stores nothing and belongs to G-02-9, which is deferred.

Check whether `schematicOut` needs anything: it normalises nil collections, and a string field has

option:

1. **One descriptive field, no probe state.** `Usable`, `ProbedAt` and `ProbeReason` keep their

   sentences into three states. The architecture is rendered beside the verdict rather than inside
   it precisely so that rewrite does not have to carry it — which is also why this plan runs after
   02-12 rather than editing the same sentence twice.
3. **No re-probe, and the 409 path is untouched.** G-02-9's remedy would update the probe fields on
   a re-POST. That route stores nothing today and this plan does not change it.
