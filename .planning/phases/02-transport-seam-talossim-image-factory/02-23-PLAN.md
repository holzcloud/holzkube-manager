<objective>
Close the remaining half of G-02-2: the cold installer resolution still walks its two candidates one
after the other, and the operator still waits on a screen that names no ceiling.

Purpose: plan 02-22 gave the manifest GET its own budget and gave the assets route one shared
deadline, which stops the route from exceeding the response budget. It did not make the route fast —
it made it *bounded*. `resolveInstallerRepo` still issues candidate one, waits for its whole budget,
and only then issues candidate two, so a cold resolution behind a silent preferred candidate costs
one full manifest budget before the second question is even asked. That is the 43.42s measured
success (30s for the silent candidate plus 13.4s for the one that answered) and, with the shared
deadline above it, the second candidate is now the one that gets cut. Asking both at once collapses
the cold case to the slowest single candidate and, as `02-DECISION-probe-budget.md` notes, closes
G-02-3's silent-fallback window for free — a candidate that never answers no longer costs the
candidate after it its budget.

The browser half is the same defect from the far end. `web/src/api.ts` `send()` issues `fetch` with
no `AbortSignal` and no timeout, so no request in the product has a client-side ceiling at all; and
the assets panel renders a bare `Resolving…` with, in G-02-2's own words, "no error and no ceiling".
The server now knows exactly how long it may take, because it declares that number as a constant. The
screen can say it.

Output: two candidates asked at once with the declared order still deciding the winner, a composition
table that records one concurrent candidate instead of two serial ones, a browser that cannot wait
forever, and two waiting screens that state the budget the server is actually keeping.
</objective>
