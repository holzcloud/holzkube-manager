<objective>
Close G-02-4 and G-02-5: make the SecureBoot flag reach the installer repository name, and give the
package one taxonomy for what a registry answer means instead of two that disagree.

Purpose: G-02-4 is the only gap in this UAT where holzkube emits a demonstrably wrong value. With
SecureBoot ticked the ISO, PXE, disk image and cmdline all gain the `-secureboot` suffix while the
installer reference does not, so the operator is handed a SecureBoot ISO paired with the
non-SecureBoot installer — verified against the live registry, where the two installers are
different images (`f960382f…` versus `878b171c…`) selected by repository name alone. G-02-5 is the
classification asymmetry behind it: `resolveInstallerRepo` counts only an exact 404 as a refusal
while `ProbeBuildable` maps the whole 4xx class to `ErrSchematicNotBuildable`, so a 400 makes the
refusal verdict nearly unreachable in one place and a 429 becomes a permanent accusation in the
other.

Output: SecureBoot-aware installer candidates and cache key, one classifier used by both call
sites, table tests over the statuses the live Factory actually returns, a live drift check that
settles which of the four installer names answer at which version, and a corrected `DefaultTimeout`
doc comment that names the ISO HEAD and the manifest GETs the value governs — the value itself
untouched, because that is cluster A's.
</objective>

Add one unexported predicate in `probe.go`, beside `ProbeBuildable`, and make it the package's only
statement of the taxonomy:

    func registryRefused(status int) bool

True for 400 and 404, false for everything else. Its doc comment is where the rule is argued, once,
and both call sites reference it rather than restating it. The argument to write down: 400 and 404
are the registry answering about this schematic — 404 is "no manifest under that name" and 400 is
what the Factory returns when an extension in the schematic is not available at the requested
version, both reproducible and both unchanged by a retry. 401, 403 and 429 are the registry
declining to answer *us*: an authentication challenge, a policy refusal and a rate limit say nothing
about the schematic, and factory.talos.dev is known to throttle. A 429 recorded as
`ErrSchematicNotBuildable` becomes a permanent, unclearable accusation, because the probe verdict is
written once at creation and there is no re-probe path.

## Interaction with the open probe-budget decision

`02-DECISION-probe-budget.md` is open and owns G-02-1, G-02-2 and G-02-9. This plan touches neither
option, and the collisions worth naming before they are discovered are these:

1. **Task 2 enlarges the unprobed population.** Moving 429 and 403 from `ErrSchematicNotBuildable`
   to `ErrUpstreamUnavailable` means `schematics.go:243-245` stamps `ProbedAt` for strictly fewer
   answers than before, so more records end creation with no verdict. That is the correct
   classification, and it makes the question the decision document asks slightly more pressing — it
   does not answer it, and this plan must not compensate by widening what counts as a refusal.
2. **Task 1 doubles the installer cache key space, and that residue is filed rather than absorbed.**
   Putting SecureBoot in the key is required by G-02-4's second missing bullet and is not up for
   revision. Its consequence is: `?secureboot=true` no longer reuses the non-SecureBoot entry, so
   there is one additional *cold* `resolveInstallerRepo` per (platform, version). That walk is two
   serial candidates at `DefaultTimeout = 30s` each — 2 x 30s = 60.000s worst case against
   `writeTimeout = 60s`, which is precisely the composition G-02-2 measured a 502 at
   (`duration=1m0.002907792s`). This plan neither worsens that per-request ceiling nor fixes it; it
   doubles the number of requests that can arrive at it cold. Bounding it needs the per-route
   deadline `02-DECISION-probe-budget.md` owns, and G-02-2 is deferred to cluster A. T-02-45 records
   the acceptance against that work, in the same register plan 02-12 uses for its own once-per-
   interval residue — filed where the deferred work will find it, not treated as free.
3. **Option 2 remains available on top of this plan.** Option 2 of the decision document suggests
   probing the installer candidates concurrently under one shared deadline, which is also what would
   collapse the 2 x 30s composition above. That remains reachable: `installerCandidates` returns an
   ordered list and says nothing about how the list is walked, so a later concurrent walk preferring
   the platform-prefixed 2xx changes `resolveInstallerRepo` alone.
4. **No budget in this package is touched.** `DefaultTimeout`'s value, `writeTimeout` and the absence
   of a per-route deadline are all cluster A. Task 2 corrects `DefaultTimeout`'s doc comment — the
   one item the decision document lists as unconditional under both options because it changes no
   value — and nothing else. If a task here appears to need a budget raised, stop and say so rather
   than raising it.
