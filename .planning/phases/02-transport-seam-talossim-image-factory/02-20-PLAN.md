<objective>
Close G-02-17 and G-02-11: two unguarded doors in a request body whose siblings are guarded, and a
browser guard that stops one codepoint short of every class the server refuses.

Purpose: `schematicInput.validate` checks that `name` is non-empty and that `talos_version` and
`arch` are well formed. Neither `name` nor `cluster` passes through the refusal predicate or any
control-character check at all. A POST with NUL and RLO in the name returned `201`, was stored
verbatim, and rendered raw in the saved table including the bidi override — while `kernel_args` and
`meta`, arriving in the same request body, are guarded. Two doors in one wall, one of them locked.

The browser half is the same defect from the other side. `hasControlCharacter` tests only
codepoints below U+0020, U+007F and the surrogate range, so U+2028, U+FEFF, U+0085, U+200B, U+202E
and U+00A0 all pass the form. Plan 02-14 measured which of those the Factory actually diverges on
and widened the server's set accordingly; this plan makes the browser's set the same set and adds
the drift guard that keeps them the same. It is deliberately sequenced after 02-14 for exactly that
reason — a guard specified before the divergence set was known would have been another guess.

The third thing is the lone surrogate. `encoding/json` rewrites an unpaired surrogate to U+FFFD
before `validate` ever sees the string, so a non-browser caller gets a schematic id computed over a
character they never sent, and a `201`. Commit `ec10e08` refused it at the browser input, which made
the server's `utf8.ValidString` branch unreachable from the form but left API clients exposed —
WINDOWS entry 29 records this as T-02-67 and says the honest fix is a raw-bytes check before
decoding.

Output: one predicate with two call sites, two more fields behind it, a decided surrogate contract,
a browser guard pinned to the server's, and a saved table a stored bidi control cannot reorder.
</objective>
